--------------------------------------------------------------------------------
1. WHAT THE MODEL IS / WHAT IT DOES
--------------------------------------------------------------------------------
Krea Realtime 14B is a 14-billion-parameter AUTOREGRESSIVE REAL-TIME TEXT-TO-VIDEO
model. Unlike a normal diffusion video model that denoises the whole clip at once,
it generates the video BLOCK BY BLOCK (a "block" = one autoregressive chunk of
frames). Each new block is conditioned on the KV-cache / context of the blocks
already generated, which is what makes streaming / real-time generation possible.

Sources:
  - https://www.krea.ai/blog/krea-realtime-14b
  - https://huggingface.co/krea/krea-realtime-video
  - https://github.com/krea-ai/realtime-video

Pipeline components (loaded independently via from_pretrained(subfolder=...),
no full upstream pipeline is ever instantiated):

  Component        | Class               | Source repo                        | Params
  -----------------|---------------------|------------------------------------|--------
  Text encoder     | UMT5EncoderModel    | Wan-AI/Wan2.1-T2V-14B-Diffusers    | 6.73 B
  Transformer (DiT)| CausalWanModel      | krea/krea-realtime-video           | 14.29 B
                   | (trust_remote_code) |                                    |
  VAE (3D causal)  | AutoencoderKLWan    | Wan-AI/Wan2.1-T2V-14B-Diffusers    | 0.13 B

Inference configuration currently used on TT (qb2-blackhole, 4 chips, mesh 1x4):
  - dtype                bfloat16
  - resolution           480 x 832   (latent 60 x 104, VAE scale factor 8)
  - inference steps      6
  - frames per block     3   -> 9 output frames per block after VAE temporal upsample
  - NUM_BLOCKS           1   (multi-block still blocked, see section 5)
  - text token length    512
  - sequence length      32760 ; frame seq length 1560 ; KV cache size 9360
  - local attention size 6 (KV_CACHE_NUM_FRAMES 3 + NUM_FRAMES_PER_BLOCK 3)
  - mesh                 2D (batch, model) SPMD; supports 1/2/4/8/32 devices
                         MESH_SHAPES = {32:(8,4), 8:(2,4), 4:(1,4), 2:(1,2), 1:(1,1)}
  - demo prompt          "a cat sitting on a boat", 24 fps, mp4 output

[S5] tt-xla #4465  - CLOSED 2026-07-17
     "[Krea Realtime 14B] VAE decoder: RuntimeError: Value out of range

     unannotated, so UpdateGlobalToLocalShapes produced mismatched global vs per-shard
     shapes. Fixed by tt-mlir PR #8492.

[S7] tt-xla #5551  - CLOSED 2026-07-10
     "[Krea Realtime 14B] transformer - Device count mismatch: 8 vs 1"
     Root cause: no-input const-folded graph (torch.arange in RoPE) stamped with a 1x1
     mesh, collapsing the real device mesh. Fixed by PR #5531.

[S8] tt-xla #5624  - CLOSED 2026-09-03
     "[Krea Realtime 14B] OOM in transformer"
     Symptom: "Out of Memory: Not enough space to allocate 383385600 B DRAM buffer".
     Root cause identified as RoPE sub-tile padding: Krea expresses RoPE as
     view_as_complex(x)*freqs -> view_as_real().flatten(), which after complex
     decomposition becomes a butterfly of ops on (..., D/2, 1) tensors; a trailing dim
     of 1 pads to a full 32x32 tile, so each buffer is ~32x its logical size (a
     4680x10x64x1 f32 tensor becomes a 383 MB DRAM buffer; six of them -> ~2.67 GB peak).
     The fix attempt (tt-mlir#9024) was closed - see section 6. Ticket was ultimately
     closed because on current main the transformer runs without OOM at NUM_BLOCKS=1
     (the target hardware moved to qb2-blackhole, where the transformer already passes).

[S9] tt-xla #5696  - CLOSED 2026-08-17
     "[Krea Realtime 14B] Add PCC gated nightly test & demo for E2E pipeline in QB2 blackhole"
     Task ticket. Closed by PR #5838 + tt-forge-models#844.

[S10] tt-xla #5835  - CLOSED 2026-09-03   (best-documented root cause of the set)
     "[Krea Realtime 14B] OOM in PCC-gated nightly test"
     Symptom: the component test passed with 0 recompiles, but the e2e pipeline died on
     the SECOND forward (b0_step1) with a fragmented DRAM OOM (DRAM 94.7% full; 225 MB
     free per bank but largest contiguous block 44.1 MB vs 47.9 MB needed).
     Root cause: stock self-attention derives its KV-cache write position from mutable
     Python-int counters kv_cache["global_end_index"] / ["local_end_index"], which flip
     0 -> 4680 between denoising steps. torch.compile captures those as GUARDS, not
     tensors, so the 2nd forward fails the guard and recompiles. Because tt_torch sets
     inline_inbuilt_nn_modules=False the recompile is per-layer: one counter flip caused
     136 recompiles / 7548 check_obj_id guards across 40 layers, each recompiled graph
     allocating fresh DRAM until the pool was fragmented past use.
     Fix: under local_attn_size == -1 (the shipped default) the counters cancel out in
     the write-position arithmetic, so they can be pinned to 0 before the stock forward.
     Implemented as apply_krea_static_patches in tt-forge-models#844.

[S11] tt-xla #6038  - CLOSED 2026-09-02
     "[Krea Realtime 14B] e2e pipeline fails on fresh HF cache - encoders.py never
      fetched (ModuleNotFoundError)"
     Root cause: the pipeline imports encoders.py for prompt_clean, but
     trust_remote_code=True only downloads the auto_map closure (causal_model.py,
     attention.py, model.py). The dev machine already had encoders.py cached from earlier
     CPU-parity runs, which masked it; the first clean-cache run exposed it.
     Fixed by tt-forge-models#916.

[O4] tt-xla #6047  - OPEN (since 2026-09-05)  ** BLOCKS VAE-ON-TT FOR MULTI-BLOCK **
     "[Krea Realtime 14B] Resident transformer memory blocks VAE decoder on TT"
     The VAE decoder works standalone on TT but OOMs inside the e2e pipeline, purely
     because of what the transformer leaves resident.
     Measurements (per chip, 8 banks x 4074 MB per bank):
        resident after step 5 (before decode) : 27.5 GB   (3440 MB / bank)
        expected sharded weights              : ~7.15 GB  (~894 MB / bank)
        expected KV + cross-attn caches       : ~2.1 GB   (~263 MB / bank)
        free before decode                    : 5.1 GB    (634 MB / bank)
        largest contiguous free               : 2.7 GB    (341 MB / bank)
        decoder peak demand                   : 1428 MB (frame 2), single buffers ~660 MB
        OOM point                             : PermuteOp in frame 1, 153 MB/bank request
     Root cause: memory growth is linear in newly compiled programs - 263 -> 3240 MB over
     the 217 programs compiled in step 0 (~116 MB/chip each, roughly one layer's sharded
     weights), +200 MB over 27 recompiles in step 1, then flat. ZERO executables are ever
     destroyed. So ~18 GB/chip is the transformer weights held in multiple per-program
     copies. Weights themselves are correctly sharded; text encoder is correctly freed.
     Current workaround (in PR tt-forge-models#920): for num_blocks == 1 the pipeline
     drops the transformer, its caches and the dynamo graphs before _decode.
     NOT viable for num_blocks > 1, because the transformer runs again after each decode
     and from block 2 on it consumes decoded frames through the VAE encoder.
     The real fix is executable/program memory reclamation in the runtime.
     https://github.com/tenstorrent/tt-xla/issues/6047

[P1] tt-xla #6040  - OPEN (created 2026-09-02, last touched 2026-09-19)
     "Cast mixed integer index dtypes to int64 for XLA advanced indexing"
     Fixes issue #5837 (the multi-block blocker). Advanced indexing with mixed
     int32/int64 index tensors is legal PyTorch and runs on CPU/CUDA, but torch_xla
     lowers multi-tensor advanced indexing by CONCATENATING the index tensors into one
     coordinate tensor, and XLA's concatenate requires uniform element types -> S64 vs S32.
     Hit by FlexAttention's create_block_mask (int32 arange indices meeting torch.vmap's
     int64 batch index).
     Fix: widen non-int64 integer index tensors to int64 before torch_xla lowers them,
     at BOTH entry points - _cast_int_indices_to_long in torch_overrides.py (eager,
     __setitem__/__getitem__/index_put) and a cast_index_tensors_to_long FX pass in
     backend/passes.py (compiled, wired into torch_pass_pipeline).
     New test: tests/torch/ops/test_index_put_mixed_dtype.py (eager + compiled, red
     before / green after, CPU-golden compared).
     CI: 60 SUCCESS / 5 skipped, no failures. Mergeable, but state is BLOCKED -
     i.e. WAITING ON REVIEW APPROVAL. Still unreviewed since 2026-09-02.
     https://github.com/tenstorrent/tt-xla/pull/6040
