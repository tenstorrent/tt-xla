2. MODALITY FINDINGS  (evidence, not the model card's word)
--------------------------------------------------------------------------------
SUPPORTED : text, image, text+image.
NOT SUPPORTED : audio, video.

  Image  -> config.json has vision_config (gemma4_vision, 27 layers, hidden 1152,
            patch 16, vision_soft_tokens_per_image 280), image_token_id 258880,
            boi 255999, eoi 258882.
            modeling_diffusion_gemma.py@v5.12.0 L994 vision_tower, L1002
            get_image_features, L1055/L1061 pixel_values + image_position_ids.
  Audio  -> no audio_config, no audio_token_id, no audio tower. grep audio in
            config.json = 0 hits.
  Video  -> modeling_diffusion_gemma.py@v5.12.0 L975 states verbatim:
            "it doesn't support audio or video inputs". No pixel_values_videos.
            grep video in config.json = 0 hits.

  *** TRAP (important) ***
  Audio LOOKS supported at three layers above the model:
    - tokenizer_config.json DOES define audio_token <|audio|>, boa <|audio>, eoa <audio|>
    - processor_config.json DOES carry a full Gemma4AudioFeatureExtractor
      (16 kHz mel, audio_seq_length 750, 40 ms/token)
    - chat_template.jinja DOES render <|audio|> and <|video|> parts
  Gemma4Processor's guard (processing_gemma4.py L147) only fires when the
  TOKENIZER lacks an audio token -- and this tokenizer has one. So audio inputs
  would be BUILT WITHOUT ERROR, embedded as ordinary text tokens with no features
  scattered in, and the model would emit plausible garbage.
  => Audio fails SILENTLY. Always take config.json + modeling source as the
     authority, never the processor/tokenizer/template stack.

  The HF and Google model cards claim frames-based VIDEO support. That
  CONTRADICTS modeling L975. Code was followed over the card.

4b. PER-COMPONENT PCC -- IMAGE-ONLY PATH  (via runner YAML, floors held at 0.99)
--------------------------------------------------------------------------------
  component            variant                 input        PCC
  vision tower alone   vision-tower            image        >= 0.99   PASS
  encoder              encoder                 text         0.9756266115561364
  encoder              encoder-image-only      image-only   0.8687509833287677
  full model           26B-A4B-it              text         ~0.949 (see sec 5)
  full model           26B-A4B-it-image-only   image-only   RuntimeError
                                                            Bad StatusOr access:
                                                            INTERNAL: Error code: 13

  READ:
  * The vision tower is NOT the cause. It clears 0.99 standalone, replicated,
    with the real candy.JPG patches -- the same config it runs in inside the
    encoder. This RULES OUT the gemma4 issue #5277 explanation ("embedder towers
    replicated -> PCC loss") for DiffusionGemma. Do not cite #5277 here.
  * Same encoder component: text 0.9756 -> image-only 0.8688 = -0.107.
    The loss is IMAGE-SPECIFIC and sits between the tower and the text layers.
    Two candidates, both untouched by the text path:
      (a) the masked_scatter merge of soft-token features into inputs_embeds
          (data-dependent boolean indexing, EncoderModel.forward ~L1083-1096)
      (b) the bidirectional vision attention mask -- text_config
          .use_bidirectional_attention == "vision" routes mm_token_type_ids
          through get_block_sequence_ids_for_mask (torch.roll/cumsum/where) into
          create_masks_for_generate. Never exercised on the text path.
    NOT yet discriminated between (a) and (b).
  * The full-model runtime failure is SEPARATE from the accuracy gap. Both halves
    work in isolation; only the combined encoder+decoder+lm_head graph fails, and
    it reproduces at 277 tokens (image-only) as well as 284 (image+text) -- so
    sequence length is NOT the trigger, and the lm_head shard did not fix it.
    Consistent with the staged-residency rationale (#5538) that this model cannot
    run as one monolithic graph.
    NOT AN OOM -- verified by grepping the full 10,961-line log: zero hits for
    "Out of Memory", "bank_manager", "largest free block", "bank size", TT_FATAL.
    The earlier genuine OOM (runner_image2.log) printed the full allocator report
    plus TT_FATAL @ bank_manager.cpp:462, so this backend reports DRAM exhaustion
    loudly and did not here. The lm_head shard fixed the memory problem for good.
    The resource-limit theory is therefore CONTRADICTED, not just unproven.
    "Error code: 13" arrives with no diagnostic at all, i.e. not through the normal
    tt-metal assert path. Next step to chase it: re-run with TTXLA_LOGGER_LEVEL=DEBUG
    (or VERBOSE) to capture what the runtime reports before the StatusOr unwrap.

    - variants 26B-A4B-it-image (image+text) and 26B-A4B-it-image-only

    - load_text_inputs / load_image_inputs / load_inputs variant dispatch
      (the runner passes only dtype_override+batch_size, so variant is the only
       channel to request images). prompt="" gives the image-only path.
    - shared _apply_chat_template + _finalize_inputs (drops unused_input_names,
      batches, casts; cast_input_to_type is category-safe so only pixel_values
      follows dtype_override and the id/position tensors stay integer)
    - load_shard_spec vocab-shards lm_head FOR IMAGE VARIANTS ONLY, so the text
      variant's spec stays byte-identical

  tt_forge_models/diffusiongemma/pytorch/pipeline.py
    - TTEncoder + encoder_forward thread pixel_values / image_position_ids
    - manual_generate pops VISION_INPUT_KEYS after prefill (image is in the KV
      cache by then; it must not follow into the denoising steps)
    - DiffusionGemmaConfig(image=, image_url=), generate(image=, image_url=)
    - decoder residency keeps its own manual lm_head mark_sharding (unchanged)

  tt-xla
    - test_diffusiongemma_e2e parametrized [text]/[image], per-modality
