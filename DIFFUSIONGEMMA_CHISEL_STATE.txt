KEY COST FINDING
----------------
Accumulation mode keeps a host golden pool of every live SSA until deallocate, so
throughput decays monotonically: 13603 -> 525 -> 38 records/100s on the same model
(~18 h for the vision tower alone). Isolation holds a flat ~793 records/100s.
=> Split the two questions:
     isolation Chisel  -> "is any single op broken?"   (per op)
     probe_layers2.py  -> "does error compound?"       (per layer, cumulative)
Promotions do NOT affect isolation validity: isolated goldens are computed from
each op's own device inputs, never from the pool.

RESULT SO FAR (the actual finding)
----------------------------------
No single op is broken. Every arithmetic op is >= 0.9999 isolated, across the
vision tower, embed_vision and (so far) the encoder text stack. Yet the composed
encoder output measures 0.8867 on the image path (0.9844 on text). So the drop is
NOT one bad op -- it is accumulation across ~8,500 ops, and/or the composition
steps that exist only in the fused graph (the masked_scatter merge of soft tokens
into text embeddings, and each component inheriting the previous one's error).
Run 2 is what quantifies the per-layer compounding.

The only "failure" Chisel reports is an artifact, not a defect:
  ttnn.full with fill_value=0x7FC00000 (NaN), 2520x1, in main_const_eval_207.
  metrics.py:61 returns hard 0.0 when one side is all-NaN and the other is not.
  1 op instance. PCC is meaningless for a NaN sentinel either way.

CONCLUSION (3 of 4 cases in, 4th pending)
  No op, no block, no layer is at fault in the encoder. The drop is accumulation,
  and its RATE is set by sequence length. NOTE this restores the framing of issue
  #6054 ("Encoder PCC decays with sequence length"), which had been retracted --
  that retraction was about DECODER step PCC, not the encoder.

COVERAGE ARGUMENT (why the 3 stages are not redundant)
  Chisel isolation computes each op's golden from that op's ACTUAL DEVICE INPUTS,
  so a corrupted upstream value is inherited and the op still PASSES. There are
  8,604 mid-graph golden promotions in the image run. Isolation validates
  arithmetic GIVEN inputs, never the inputs themselves. Only the per-layer probe
  (independent CPU reference) covers that, so it is load-bearing, not corroborating.

ROOT CAUSE FOUND AND FIXED (tt-xla #6075)
  softmax over an axis that is also the SHARDED CONTRACTING DIM of a following
  matmul returns +-Inf. Confirmed in the compiled IR: the softmax decomposes to
  max -> sub -> exp -> sum -> div, and the cross-device combine of the per-shard
  MAX is emitted as stablehlo.add instead of stablehlo.maximum. Shift becomes
  max0+..+max7 (~298) instead of max(max0..max7) (~37), exp() underflows to 0,
  denominator 0, 0/0 -> +-Inf.
  Source: ShardyCCLToStableHLOCCLPatterns.cpp:310-314 hardcodes AddOp for EVERY
  sdy.all_reduce ("shardy does not have support for custom reduction types").
  Isolation: softmax alone clean; sharded matmul alone clean (0.999993);
  replicated weight clean (0.999808); sharded NON-contracting dim clean
  (0.999814); sharded CONTRACTING dim -> 308,128 inf. Not about device count.
  Issue updated with root cause + suggested fix. Repro:
  repro_softmax_sharded_matmul_inf.py (30 lines, random data, no model).
