1. THE PROBLEM
--------------------------------------------------------------------------------
imagegen_benchmark.py ran a warmup pass then a steady pass and published only the
steady one. Five imagegen pipelines EVICT every component inside generate().
Eviction discards the compiled graph along with the weights, so the "steady" pass
was a full rebuild reported as warm.

Second, deeper problem found while fixing it: the two designs published the SAME
METRIC NAMES for DIFFERENT QUANTITIES, so nothing on the dashboard compared.

--------------------------------------------------------------------------------
2. THE TWO DESIGNS
--------------------------------------------------------------------------------
SET 1 (resident): components stay on device. Harness runs a 1-step warmup pass +
  an N-step steady pass. WARM = the steady pass. COLD = the warmup pass (which the
  harness previously ran and threw away — the only honest source of a cold number
  for a resident model, since its compile happens there).
  Models: Playground-v2.5, SD-1.5, SD-3, SDXL-Lightning, FLUX.1, Z-Image,
          HiDream-I1, HunyuanImage-2.1.
  NB: Z-Image is set 1. It EVICTED before this work; making it resident is part
  of the #6010 fix. Do not mistake it for set 2.

SET 2 (staged): components are evicted inside generate() because they cannot all
  fit. ONE call only. COLD = the functional first forward; WARM = an in-residency
  repeat taken before eviction.
  Models: FLUX.2, Qwen-Image, DiffusionGemma.

The single switch the harness reads is the pipeline class attribute:
    benchmark_staged_residency = True | False
Read via getattr(..., False), so any pipeline that never heard of it degrades to
set 1 safely.

--------------------------------------------------------------------------------
3. _perf SCHEMA (pipeline -> harness contract)
--------------------------------------------------------------------------------
    _perf = {
      "components":      {name: functional_forward_s},   # stage TOTAL per call
      "steps":           [s, ...],                       # per denoise step
      "step_metric_name": str,
      "total":           s,                              # REQUIRED; raises if None
      "cold":            {name: s},   # optional, set 2
      "warm":            {name: s},   # optional, set 2
      "staging":         float,       # NEW, default 0.0 — host<->device weight
                                      # movement, mark_sharding, torch.compile
                                      # construction, gc.collect, torch_xla.sync
      "synthetic":       float,       # NEW, default 0.0 — seconds burned in
                                      # discarded warm-repeat passes
    }
Both new keys default to 0.0, so untouched pipelines keep working unchanged.

--------------------------------------------------------------------------------
4. PUBLISHED METRICS — identical keys and meaning in BOTH designs
--------------------------------------------------------------------------------
  <name>_s            warm forward (== <name>_warm_s)
  <name>_warm_s       warm forward
  <name>_cold_s       cold forward (set1: from the warmup pass; set2: _perf["cold"])
  <step>_mean_s       mean(steps[1:])   == <step>_warm_s
  <step>_cold_s       steps[0]  (set1: the warmup's steps[0])
  cpu_overhead_s      total - Sum(components) - Sum(steps) - staging - synthetic
                      SIGNED, not clamped (a clamp would hide an over-counting
                      timer as a perf win); warns when negative
  staging_overhead_s  staging      (set1 ~0, set2 ~350)
  synthetic_s         synthetic    (set1 0, set2 ~9.75)
  e2e_warm_s          Sum(warm comps) + N*warm_step + cpu_overhead
  e2e_cold_s          Sum(components.values()) + cold_step + (N-1)*warm_step
                      + cold_overhead + cold_staging
  e2e_latency         measured wall clock of the measured pass (per-design, honest)
  images_per_second   total_samples / steady_state_time  (wall clock)
  warm_e2e_latency_s  DELETED — replaced by e2e_warm_s

  NOTE on e2e_cold_s: it sums the STAGE TOTALS (components.values()), not the
  single cold forwards, because a stage may run more than one functional forward
  per call (Z-Image and Qwen-Image encode two prompts) and a cold generation pays
  for all of them. Verified: real FLUX.2 still reconciles exactly.

  N = len(steps), NOT num_inference_steps — pipelines that fold a CFG pair into
  one timed step (Z-Image, Qwen-Image) report fewer entries than steps requested.

  step_warm_up_num_iterations = 1 on warm measurements, 0 on cold, so the
  distinction survives without name-parsing.

M1 INVARIANT (used by the metric checker):
    for staged models:  e2e_latency - e2e_cold_s - synthetic_s ~= 0
Verified on real FLUX.2: gap = 93 microseconds.

6. SINGLE-PIPELINE RESTRUCTURING (SDXL-Lightning + Playground-v2.5)
--------------------------------------------------------------------------------
Every touched model now has ONE pipeline in tt_forge_models serving three callers:
    - PCC-gated e2e test  (tests/torch/models/<m>/test_<m>_pipeline.py)
    - demo                (examples/pytorch/<m>.py)
    - benchmark           (tests/benchmark/test_imagegen.py::test_<m>)
There are THREE seam styles, all declared BY THE SHIPPED PIPELINE — no caller
reimplements generate(), verified by grep:
  a) _check(self, name, tt_out, *cpu_inputs)      -- sdxl_lightning, playground_v2_5
     no-op in the shipped pipeline; the test overrides it and loads an fp32 CPU
     twin per component.
  b) _intercept(self, name, compiled) [+ _pre_place]  -- flux, flux2, z_image
     the test wraps the compiled callable as it is installed.
  c) class-attribute injection                     -- qwen_image
     TEXT_ENCODER_CLS / DENOISER_CLS / VAE_CLS on the pipeline; the test
     subclasses the device wrappers and swaps them in.
All three are hooks, not copies. Residency/graph handling is INHERITED, never copied,
so the test exercises the shipped pipeline rather than a copy that can drift.
The trajectory is advanced with the DEVICE output (deployment behaviour), so a PCC
drop anywhere fails the test rather than silently degrading the image.
This eliminated 2060 duplicated lines across 6 files.
